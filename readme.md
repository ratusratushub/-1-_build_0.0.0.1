# Space Simulation Foundation

Модульная основа нативного 3D-симулятора на C++20 / OpenGL 4.3. По умолчанию создаются 1000 воспроизводимых случайных частиц в кубе XYZ `[-500, +500]³`. Мир содержит 10×10×10 чанков размером 100³. Центральное массивное тело закреплено в `(0,0,0)`.

Добавлены исходники настоящего 3D-рендерера, свободной камеры, интерфейса Dear ImGui, GPU-физики Velocity Verlet и пространственного индекса. **Сборка, запуск C++ и визуальная проверка в текущем окружении не выполнялись.** Пройденные Python-проверки не заменяют эти проверки. Полный статус — в [отчёте](docs/REPORT.md), причины изменений — в [аудите](docs/AUDIT.md).

Это нативное приложение, которому требуется графический контекст. Оно не запускается как веб-страница или сервер Netlify.

## Зависимости и запуск

Нужны CMake 3.24+, C++20-компилятор, Git, Python 3 с Jinja2 (генерация GLAD), драйвер с OpenGL 4.3 и библиотеки разработки оконной системы. Для Linux/GLFW обычно нужны X11 development headers (`xorg-dev`), `libwayland-dev`, `libxkbcommon-dev` и `wayland-protocols`; конкретный список зависит от дистрибутива. Native OpenGL в macOS ограничен 4.1 и не поддерживает этот compute-проект.

CMake загружает закреплённые версии GLFW 3.4, GLAD 2.0.8, GLM 1.0.1 и Dear ImGui 1.91.8. GLFW/GLAD уже использовались; GLM добавлен для матриц и камеры, Dear ImGui — для компактного интерфейса. Дополнительного движка, оконного фреймворка и системы ресурсов нет.

```sh
cmake -S . -B out -DCMAKE_BUILD_TYPE=Release
cmake --build out --config Release --parallel
ctest --test-dir out -C Release --output-on-failure
./out/space_sim
```

При многоконфигурационном генераторе исполняемые файлы обычно находятся в `out/Release/`. Каталог шейдеров задаётся CMake абсолютным путём к исходникам: при переносе приложения необходимо сохранить исходный путь или пересобрать его на новом месте.

```sh
./out/space_sim --count 1000 --seed 42 --mass 100000 --softening 5
./out/space_sim --count 257 --exact
./out/space_sim --hidden --frames 120 --no-vsync
./out/space_sim --help
```

`--exact` включает дополнительную точную взаимную гравитацию частиц, ограниченную 4096 частицами из-за O(N²). Без этого флага частицы испытывают только силы массивных тел. Дополнительные параметры: `--radius`, `--min-mass`, `--max-mass`, `--min-velocity`, `--max-velocity`, `--step`. Размер мира и количество чанков меняются независимо от количества частиц в `SimulationConfig::world`. По умолчанию время работы не ограничено; `--frames` ограничивает количество отображённых кадров.

Для CPU-тестов без GPU, оконной системы, GLM, ImGui и сетевого скачивания зависимостей:

```sh
cmake -S . -B out-cpu -DSPACE_BUILD_APP=OFF -DCMAKE_BUILD_TYPE=Release
cmake --build out-cpu --parallel
ctest --test-dir out-cpu --output-on-failure
```

## Управление

| Действие | Управление |
|---|---|
| Горизонтальное движение | WASD |
| Вверх / вниз по Y | Space / левый Ctrl |
| Поворот камеры | Зажать правую кнопку мыши и двигать мышь |
| Скорость камеры | Колесо мыши |
| Ускоренное движение | Левый Shift |
| Вернуть камеру | R |
| Направить взгляд на чёрную дыру | F |
| Pause / Resume | P или кнопка |
| Один физический шаг с переходом на паузу | N или Step |
| Перезапустить с тем же seed | Home или Restart |
| Выход | Esc |

Движение камеры использует реальное время и не зависит от Time Scale. Панель позволяет менять Time Scale, массу центрального тела и видимость чанков. Раздел Chunk operations позволяет выбрать XYZ чанка, добавить в него точки или удалить все его частицы. Оси: X красная, Y зелёная, Z синяя. Восемь чанков, примыкающих к началу координат, выделены более светлыми гранями. Центральное тело отображается сферой с тёмным ядром и различимой каймой, с настоящим тестом глубины. Визуальный радиус не меняет гравитацию.

## Устройство данных и чанков

`EntityManager` хранит независимые непрерывные GPU-потоки `vec4 position/mass`, `vec4 velocity`, `vec4 acceleration`, `uint membership` и `uint identity`. Постоянный ID отделён от физического слота: при обычной индексации пересортировываются только ссылки, а при удалении чанка частицы уплотняются на GPU с сохранением ID. `append()` добавляет новые последовательные ID без повторного использования в текущей симуляции. `clear()`/перезапуск начинают новую симуляцию с ID от нуля; диагностический `setState()` также создаёт новую нумерацию. Переполнение 32-битного пространства ID отклоняется.

Память выделяется под фактическое количество с геометрическим ростом ёмкости, а не под 10 миллионов при запуске. `reserve()` сначала создаёт новые буферы и копирует живые данные на GPU; при ошибке сохраняет прежние буферы. При росте возможен значительный временный пик памяти. Инициализация использует не более 65 536 записей staging на поток, а при 1000 частицах — 1000 записей. Генерация использует seed и ID; объёмное распределение, массы и скорости воспроизводимы независимо от размера пакета.

`World::locate()` и общий GLSL-файл `grid.glsl` задают одинаковые границы:

- базовое правило `floor((position + halfExtent) / chunkSize)`;
- коррекция сравнением с гранями через FMA предотвращает ошибки округления около внутренних границ, включая маленькие отрицательные координаты около нуля;
- внутренние интервалы полуоткрытые; внешняя положительная граница +500 включена в последний чанк;
- NaN, Inf и координаты вне куба не прижимаются к краю;
- CPU возвращает `outsideChunk`, GPU использует дополнительный bucket 1000;
- внешние частицы продолжают свободное движение под гравитацией. Отражения, периодичности и невидимой стены нет.

После каждого физического шага GPU строит компактный индекс за histogram → exclusive prefix → scatter. Индекс содержит `counts`, `offsets` и список ID-слотов. Чанк `c` владеет диапазоном `slots[offsets[c]..offsets[c+1])`. На частицу приходятся две целочисленные атомарные операции. CAS-суммы float удалены из рабочего пути. Prefix выполняется одним GPU-потоком по 1001 bucket; для большого количества чанков потребуется параллельный scan.

На CPU `ChunkManager` содержит hash map только занятых чанков с координатами, границами, количеством и историческим смещением из последнего снимка статистики. `clear()` очищает каталог, `update()` динамически пересобирает его из гистограммы; это не удаление физических частиц. Для физического удаления есть `ComputePipeline::clearChunk(id)`: GPU уплотняет оставшиеся позиции, скорости и постоянные ID, CPU получает только счётчики. Операция требует временных GPU-буферов и синхронного ожидания; она вызывается только явно, не в кадре. `EntityManager::append(count, config, chunkId)` равномерно заполняет указанный чанк; после append вызывается `reindex()`. После удаления сохраняется консервативная верхняя оценка общей массы для безопасного dt; она обновляется точно при restart/setState. Текущие диапазоны необходимо читать на GPU через `offsetBuffer()`: `snapshotOffset` из CPU-каталога относится к запаздывающему снимку, а не к текущему GPU-списку. Каталог не участвует в расчёте сил.

GPU использует небольшую плоскую директорию для ограниченного кубического мира и разреженные диапазоны частиц. Пустые чанки не запускают интеграцию частиц и не имеют C++-объектов в активном каталоге. Метаданные всё же требуют O(C) очистки/scan для C чанков. Это не бесконечный spatial hash: для неограниченного мира нужен GPU hash или иерархия; текущая конфигурация ограничена 128 чанками на ось.

`countNeighbors(radius)` выполняет настоящий GPU-поиск: выбирает пересекающиеся чанки, читает их компактные диапазоны и фильтрует кандидатов по расстоянию. Радиус независим от размера чанка. Результат — GPU-буфер количества соседей на частицу; CPU-чтение для обычной работы не требуется. Это диагностический/расширяемый интерфейс, не искусственное ограничение радиуса гравитации. Переполненный внешний bucket проверяется отдельно. При плотном заполнении одного чанка, большом радиусе или множестве вышедших из мира частиц поиск может деградировать до O(N²).

## Физика и синхронизация

Сила использует потенциал Пламмера: `a = G M (source-position) / (distance² + softening²)^(3/2)`. Центральное тело имеет массу 100000, softening 5, G=0.1, визуальный радиус 12. Оно не поглощает частицы. Это ньютоновская модель смягчённого массивного объекта, без общей теории относительности, горизонта событий и столкновений.

Один подшаг:

1. Force pass читает неизменные позиции и записывает ускорения.
2. Половинный kick и полный drift обновляют скорости и позиции.
3. Новый force pass вычисляет ускорения в новых позициях.
4. Второй половинный kick завершает Velocity Verlet.
5. GPU обновляет принадлежность чанкам, compact ranges и снимок статистики.
6. Рендерер читает тот же position buffer как vertex stream, без CPU-копирования. Это также избегает зависимости от поддержки SSBO в vertex shader на минимальной реализации GL 4.3.

Между фазами стоят SSBO memory barriers. Для последующего рендера и копирования предусмотрены vertex-attrib и buffer-update barriers. Force-pass с точной взаимной гравитацией никогда не выполняется одновременно с записью позиций. GPU-индекс строится из актуальных позиций, без кадрового запаздывания.

Physics clock использует фиксированные подшаги. Time Scale увеличивает их количество, а не размер. Шаг ограничен конфигурацией и консервативной оценкой `0.05/sqrt(G*totalSourceMass/softening³)`, с верхним пределом 1/120 с. Pipeline отвергает небезопасный шаг. На кадр допускается до 32 подшагов; избыток времени отбрасывается и показывается в интерфейсе. Это защита от спирали задержек, а не ускоренная симуляция пропущенного времени. Критерий по частоте смягчённого поля не гарантирует разрешения всех быстрых близких пролётов: для новых сценариев нужны проверки сходимости по dt.

Система поддерживает до 256 внешних массивных тел. В демонстрации чёрная дыра закреплена; силы всех тел вычисляются одинаково. Сохранённый `advanceMassiveBodies()` переработан на Verlet для отдельной малой CPU-системы с поддержкой закреплённых тел. Для полностью связанной эволюции движущихся массивных тел и частиц понадобится согласованное обновление источников на обеих фазах. Обратное влияние частиц на внешние тела отсутствует. Изменение массы через интерфейс меняет потенциал извне и потому не сохраняет энергию.

Старый агрегированный `SpatialGrid` сохранён как отдельный экспериментальный компонент, с тестами COM и проверкой входных значений. В основной симуляции его приблизительные силы не используются. Режим `--exact` не исключает частицы своего чанка и учитывает все пары для сравнения с CPU-эталоном. Применение точного O(N²) режима к 10M запрещено явно.

CPU получает только небольшие асинхронные снимки гистограммы через тройной буфер и fences с нулевым timeout при опросе. При занятых слотах снимок пропускается; CPU-статистика может отставать на несколько шагов и отмечена звёздочкой. CPU-каталог обрабатывается worker task; OpenGL остаётся на главном потоке. В полёте не больше трёх физических шагов: ограничитель может ждать GPU, но не читает частицы. Timer queries измеряют force/integration/indexing, исключая CPU и копию статистики, и читаются после готовности.

## Ресурсы GPU и 10 миллионов

Базовые данные занимают 60 байт на слот: 48 байт позиции/скорости/ускорения и по 4 байта membership, постоянный ID и compact slot-list. При ёмкости ровно 10M это 600 MB (~572 MiB), без оконных буферов, драйвера и временного пика роста. Дополнительный neighbor-count buffer выделяется по запросу и добавляет 40 MB. CPU никогда не зеркалирует эту популяцию в кадре.

Каждый vec4 SSBO на 10M занимает 160 MB. OpenGL 4.3 гарантирует только 128 MiB на блок: такой GPU ограничит приложение примерно 8.39M слотами. Проверяются лимит SSBO, bindings, local workgroup size/invocations, количество workgroups и ошибки выделения. Автоматическое разбиение dispatch на пакеты уже есть; оно **не отменяет** ограничение размера одного SSBO. При недостаточном лимите приложение выдаёт ошибку, не пишет за границу буфера. Портативного счётчика свободной VRAM в GL нет: окончательная проверка — результат выделения памяти.

Для 10M на GPU с достаточным SSBO архитектура не требует изменения формата частиц или чанков, но реальная скорость не измерена. Для поддержки 10M на минимальном GL 4.3 потребуются сегментированные буферы. Следующие задачи масштабирования: profiling GPU timer queries, распределённые/локальные histogram reductions при высокой конкуренции атомиков, GPU scan для большого числа чанков, LOD/culling рендера, GPU hash для неограниченного мира и Barnes–Hut/FMM для дальней взаимной гравитации с проверкой ошибки относительно `--exact`. Эти оптимизации не включаются как будто они уже реализованы.

## Проверки

```sh
python3 tests/check_contracts.py
ctest --test-dir out --output-on-failure
```

`check_contracts.py` проверяет регистр и существование путей, shader include contracts, SSBO bindings, guards, независимую численную модель границ/compact ranges, распределение генератора и устойчивость эталонной орбиты. Эти проверки выполнены; они не компилируют и не исполняют C++/GLSL.

`space_cpu_tests` проверяет pool, исключения, COM, пустые ячейки, индексы/границы/отрицательные координаты, миграцию sparse metadata, радиусы запросов, генератор, рост ёмкости, смягчение, энергию орбиты, Verlet массивных тел и управление временем.

`space_gpu_tests` создаёт скрытый GL-контекст и сравнивает CPU/GPU для 0, 1 и 257 частиц, включая оба режима гравитации. Проверяет рост с сохранением данных, удаление/заполнение чанка с сохранением ID, CPU/GPU генерацию, несколько шагов Verlet и ускорения, миграцию между чанками, граничные значения, unique scatter, prefix ranges, поиск соседей против точного перебора, гистограммы, очистку и отклонение переполнений/большого dt. При отсутствии GLFW/GL 4.3 возвращает 77: CTest отмечает **Skipped**, а не Passed. Ошибки загрузчика/шейдеров/физики после создания контекста возвращают ошибку.

GPU-тестам нужен настоящий или программный OpenGL 4.3 контекст (например Mesa + Xvfb в подходящем CI). Скриншоты, проверка управления, GL debug output, GPU tests и замеры на целевой видеокарте остаются обязательным этапом приёмки. Здесь они не запускались.
